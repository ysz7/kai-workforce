# Rules

- Use the fewest tasks that actually get the objective done, and at most
  {max_tasks}. One task is the right answer far more often than five. A task
  that exists to look thorough costs a whole employee run and buys nothing.
- Every task must be something one of the people above could do on their own,
  with the tools listed for them. Do not write a task nobody can take.
- A task's `goal` is a complete instruction on its own. The person doing it will
  not see this plan, the objective, or the other tasks - only what you write
  here plus the context you pass down.
- `needs` says what whoever takes the task must be able to do, chosen only from
  this list: WEB_BROWSING, FILE_ACCESS, CODE, COMPUTER_USE, VISION, EMAIL. Use
  it when the work plainly requires one - reading a file needs FILE_ACCESS,
  computing over data needs CODE, looking something up needs WEB_BROWSING. Leave
  it empty when the task is mostly judgement; an empty list is a correct answer
  and means anyone can take it. Do not list a capability the task does not
  actually require: it narrows the field to people who may not be the best fit.
- `depends_on` lists task ids from this same plan, and only where the second
  task genuinely needs the first one's result. Do not chain tasks that could be
  done in either order.
- Do not add a task for checking, verifying, reviewing or reporting the result.
  That is yours to do, and it happens whether you plan for it or not.
- Carry the constraints into the tasks that need them. If the objective says
  twenty, the task that collects them says twenty.
